# Work queue

The consumer side of `/triage`. Each run handles **one** issue: claim it, build it, hand it back as a PR. To drain the queue without you, run `bin/agent-listener <repo>` from skill-index (a fresh session per issue; add `--watch` to follow each one in tmux or the Claude app), or `/loop 30m /work-queue` inside one session.

Every comment posted to the issue tracker starts with:

```
> *This was generated by AI while working the queue.*
```

## Labels

Read `docs/agents/issue-tracker.md` for tracker operations and `docs/agents/triage-labels.md` for label strings. If either is missing, stop and tell the user to run `/setup-matt-pocock-skills`.

This skill owns two labels beyond the triage five. If `triage-labels.md` lacks either, add its row and create the label in the tracker:

```
| `agent-in-progress` | `agent-in-progress` | Claimed by /work-queue; triage leaves it alone |
| `spec`              | `spec`              | Parent spec from /to-spec; /work-queue never picks it |
```

- `agent-in-progress`: an agent has claimed the issue.
- `spec`: the issue is a parent spec, not a ticket. `/to-spec` labels its spec `ready-for-agent` too, so without this the queue would try to build a whole spec as one ticket. Its tickets carry the work; the spec closes when they do.

## Steps

0. **Mark specs.** For each open `ready-for-agent` issue without the `spec` label, add `spec` if it has sub-issues or its body follows the `/to-spec` template (`## Problem Statement` and `## User Stories` headings). On a local tracker, skip this step: specs live in `spec.md`, outside the `issues/` folders.

1. **Release stale claims.** For each open `agent-in-progress` issue whose claim comment is more than 4 hours old and which has no linked open PR, swap the label back to `ready-for-agent` and comment that the claim lapsed. Done when every `agent-in-progress` issue either has an open PR or a claim under 4 hours old.
2. **Pick.** Take the oldest open `ready-for-agent` issue with no `spec` label, no assignee and no open blockers. If there is none, report "queue empty" and end this run.

3. **Claim.** Swap `ready-for-agent` for `agent-in-progress`, assign yourself, and comment `Claimed by /work-queue at <ISO timestamp>`. Re-read the issue: if another assignee or claim comment landed first, release yours and go back to step 2. The claim is the run's first write.

4. **Build.** Create a git worktree on a new branch `agent/<number>-<short-slug>` from the default branch, so the user's checkout is untouched. Inside it, call the Skill tool with "implement", passing the issue reference. The spec is the agent brief in the triage comment, or for a `/to-tickets` ticket, the ticket body.

5. **Hand back.**
   - **Success** (implement finished, tests and code review pass): push the branch, open a PR whose body starts with `Fixes #<number>` and summarises the brief's acceptance criteria against what changed, and label the PR `ready-for-human`. Leave the issue on `agent-in-progress`; the merge closes it.
   - **Failure** (blocked, tests red, or the brief proved wrong): push any partial branch, swap `agent-in-progress` for `ready-for-human`, and comment what blocked you and where the partial work lives.

6. **Report.** Leave the worktree in place so the user can inspect it and push follow-up fixes. Report the issue number, the outcome, the PR link, and the worktree path.

7. **Babysit the review.** Run this only when told to babysit a PR (`bin/agent-listener --babysit` resumes the session with that instruction once a run is over). A normal run ends after step 6. Poll the PR about once a minute (wait with `ScheduleWakeup` or a background `sleep 60`, never a long foreground sleep) and handle Codex's review in rounds, working in the worktree. Read unresolved review threads with `gh api graphql` and Codex's reactions with `gh api repos/{owner}/{repo}/issues/<n>/reactions`:
   - Act only on unresolved threads authored by `chatgpt-codex-connector`. Leave human comments for the human.
   - For each one, fix it, run the project's checks, push, reply on the thread with the commit SHA, and resolve it. If the push fails over SSH, push over HTTPS with the `gh` credential helper.
   - Codex reviews only when a PR opens, goes from draft to ready, or gets an `@codex review` comment, so after pushing fixes comment `@codex review` to get the next round.
   - Never treat "no unresolved threads" as done by itself: you resolve threads yourself, and none exist before Codex's first review. Codex has finished a round only when it reacts 👍 on the PR (the reaction user is `chatgpt-codex-connector[bot]`), or when a Codex review or receipt comment names the current head SHA and leaves no unresolved threads. After pushing, wait for a new receipt for the new SHA.
   - Stop polling when Codex has finished a round with nothing left to fix (above), when the PR is merged or closed, after 3 rounds, or after 60 minutes with no Codex activity. On a cap, label the PR `ready-for-human` if it isn't already and comment what is still open.
   - Report the rounds taken and anything left open, then stop and go idle; the listener closes the window after 5 idle minutes.

The run is done when the picked issue carries either an open PR labelled `ready-for-human` or the `ready-for-human` label with a blocker comment, and its worktree is left in place. A babysit run is done once step 7's stop conditions are met.
